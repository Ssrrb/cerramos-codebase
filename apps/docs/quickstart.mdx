## Start here

Cheki docs should help a merchant, operator, or engineer understand what happens from product link to paid order. Keep pages short, operational, and grounded in the screens users actually touch.

## Core workflow

<Steps>
  <Step title="Create a product link">
    A merchant publishes one product or offer as a shareable checkout link.
  </Step>
  <Step title="Buyer completes checkout">
    The buyer reviews the product, signs in, and submits the order with payment context.
  </Step>
  <Step title="Merchant reviews the order">
    The dashboard separates operational order state from payment state so staff can act clearly.
  </Step>
  <Step title="Cheki keeps the record">
    Internal product surfaces own the state. Messaging channels only notify or continue the conversation.
  </Step>
</Steps>

## Documentation standard

- Use screenshots from `apps/docs/images` when a page describes a UI surface.
- Prefer concise operational language over broad SaaS claims.
- Keep Cheki-specific behavior separate from next-forge template defaults.
- Link back to template docs when the page is about repository structure, not product behavior.

<Tip>
  If a page explains code ownership, call out whether it describes Cheki as implemented here or the original next-forge template default.
</Tip>
