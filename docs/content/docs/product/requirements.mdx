## Regla de decisión

Toda capacidad nueva debe responder una de estas dos preguntas:

- ¿reduce fricción para cerrar el pedido?
- ¿mejora la claridad operativa para el comercio?

Si no mejora al menos una de ellas de forma directa, no entra al MVP.

## Buyer flow

### Entrada y resolución

- El sistema debe aceptar tráfico desde WhatsApp, Instagram, DM o catálogo web.
- Cada `product_link` debe resolver a un solo comercio y a un solo producto u oferta vendible.
- El link debe poder invalidarse por estado, vigencia u operación del comercio.

### Experiencia de compra

- La página de pedido debe ser móvil primero y ocurrir dentro de la interfaz de Cerramos.
- Debe mostrar nombre comercial e identidad visual básica para generar confianza.
- Cada link debe vender un solo producto.
- La información mínima visible debe incluir nombre, imagen principal, precio y descripción breve.

### Configuración del pedido

- El comprador debe poder elegir cantidad.
- El sistema debe soportar una sola dimensión de variante, por ejemplo talla o color.
- El comprador puede dejar una nota opcional.
- Antes de crear el pedido, el sistema debe validar cantidad, variante y disponibilidad del link.

### Identidad del comprador

- El checkout debe permitir flujo invitado o autenticado según política del comercio y reglas del `checkout_session`.
- La identidad recurrente debe soportar Google y Apple.
- El sistema debe poder reutilizar datos previamente guardados cuando exista identidad válida.
- El producto puede incentivar login para acelerar recompra y mejorar calidad de datos, sin convertirlo en requisito universal para crear pedidos.
- El guardado de datos debe requerir consentimiento explícito.

### Datos de checkout

- El sistema debe capturar nombre, email, teléfono y modalidad de entrega o retiro.
- Si la modalidad es entrega, la dirección es obligatoria.
- El sistema debe validar completitud y formato básico antes de aceptar el pedido.

## Order lifecycle

- El sistema debe crear un `order` al cerrar correctamente el checkout.
- Cada pedido del MVP debe contener exactamente un `order_item`.
- El pedido debe asociarse a comercio, link, comprador, datos de entrega y método de pago cuando aplique.
- El sistema debe generar un resumen legible para comprador y comercio.
- Debe existir historial auditable de cambios de estado.
- El pedido debe expirar automáticamente si no es confirmado dentro de la ventana operativa configurada.
- El valor inicial recomendado para expiración es `24 horas`.
- Los pedidos expirados solo admiten consulta y trazabilidad.

### Estados mínimos del pedido

| Estado | Uso |
| --- | --- |
| `new` | Pedido creado sin pago obligatorio |
| `pending_payment` | Pedido creado y pendiente de cobro |
| `paid` | Pago exitoso, todavía sin confirmación operativa |
| `confirmed` | Pedido aceptado por el comercio |
| `expired` | Ventana operativa vencida |
| `cancelled` | Pedido cancelado por el comercio o el sistema |

## Payments

- El pago debe integrarse con proveedor externo; Cerramos no procesa dinero por cuenta propia.
- La dirección actual del MVP es migrar desde Stripe hacia **Pagopar uPay** como procesadora principal.
- El sistema debe crear una referencia de pago específica para el pedido en curso.
- El checkout de pago debe mantenerse dentro de la URL y la interfaz de Cerramos; no debe redirigir al comprador a un dominio externo en el flujo normal.
- Si el proveedor exige un paso externo excepcional, ese desvío debe tratarse como contingencia y no como experiencia base.
- Los datos sensibles de pago deben ser capturados solo por componentes certificados del proveedor.
- Cerramos puede almacenar referencias, tokens no sensibles y metadatos del método.
- El sistema debe actualizar el estado de pago por webhook, callback o conciliación.
- `paid` no equivale a `confirmed`.
- `funds_released = false` hasta que `order_confirmed = true`.
- Si la tienda no confirma dentro de la ventana operativa, el sistema debe revertir, cancelar o reembolsar automáticamente según soporte del proveedor.

## Merchant operations

- El panel interno debe ser la interfaz operativa principal del comercio.
- El comercio debe poder listar pedidos, ver detalle, confirmar, cancelar y revisar historial.
- Deben existir alertas mínimas por email o WhatsApp para pedido nuevo, pago recibido, expiración y cancelación.
- El MVP soporta una sola cuenta operativa por comercio.
- El tier inicial de onboarding solo habilita métodos de bajo riesgo:
  - pago en tienda
  - pago contra entrega

### Ownership operativo

- `orders` debe conservar ownership de estado del pedido.
- `payments` debe conservar ownership de estado del pago.
- `merchant` debe conservar ownership de configuración, políticas y habilitaciones del comercio.
- El panel debe surfacer y coordinar estos estados sin colapsarlos en un solo subsistema.
- Email, WhatsApp y otras notificaciones no son la interfaz operativa.

## Trust and risk

- El comercio debe pasar verificación básica antes de operar en producción.
- Deben registrarse señales mínimas de identidad y consistencia comercial.
- El sistema debe calcular un `trust_score` explicable internamente.
- Deben existir estados de confianza mínimos:
  - `pending_review`
  - `verified`
  - `limited`
  - `rejected`
  - `suspended`
- La política de cobro debe depender del nivel de confianza del comercio.

## Terminología obligatoria

- Usar `resumen del pedido`.
- Usar `comprobante comercial`.
- No usar `factura` para describir la salida del MVP.
