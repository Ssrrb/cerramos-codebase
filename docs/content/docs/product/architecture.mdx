## Principio rector

La arquitectura no debe diseñarse como un CRUD genérico. Debe diseñarse como una **plataforma de checkout y orquestación de pedidos**.

Eso cambia la prioridad:

- primero integridad del pedido
- luego continuidad del pago
- después operación del comercio

## Modelo de implementación

La dirección arquitectónica de Cerramos debe evolucionar hacia **servicios con límites claros y ownership explícito por dominio**.

Ese es el modelo operativo objetivo. No obliga a separar despliegues o bases de datos desde el primer día.

Para el MVP, la implementación inicial puede permanecer dentro de un **monorepo con PostgreSQL compartido**, siempre que los límites se respeten en código, contratos internos y APIs.

- frontend en Next.js
- backend dedicado en TypeScript
- PostgreSQL como núcleo transaccional inicial
- Redis para estados efímeros, throttling e idempotencia
- procesamiento asíncrono para webhooks, conciliación y expiraciones

La prioridad no es extraer microservicios de forma prematura. La prioridad es evitar que checkout, pagos y operación del comercio se mezclen sin límites.

## Módulos dominantes

- `auth`
- `merchant`
- `catalog`
- `link`
- `checkout`
- `payment`
- `webhook`
- `delivery`
- `audit`

La razón no es orden cosmético. Es preparar límites de servicio reales aunque la primera versión siga corriendo dentro de un mismo repositorio y una base compartida.

## Modelo de compra

- un `product_link` apunta a un solo producto u oferta
- un pedido contiene un solo `order_item`
- la variante permitida es de una sola dimensión
- el carrito multiproducto queda fuera de MVP

Esta restricción mantiene pequeño el sistema de precios, validación y estados.

## Identidad y buyer flow

- el checkout puede operar con comprador invitado o autenticado según política del comercio y reglas de la sesión
- Google y Apple son los caminos principales de identidad recurrente
- el login mejora recurrencia, reutilización de datos y calidad de identidad, pero no debe ser una barrera universal para crear pedidos
- la persistencia de datos requiere consentimiento

La identidad no se trata como una capa decorativa. Se trata como parte del control de calidad del pedido.

## Operación del comercio

El panel interno es la **interfaz operativa canónica**, no un contenedor único de toda la verdad del sistema.

- email y WhatsApp pueden alertar
- alerts, chats y notificaciones no deben convertirse en interfaz operativa
- el panel coordina y expone la verdad de cada dominio para que el comercio pueda actuar con claridad
- el historial de cambios debe ser auditable

Si el pedido “vive” en mensajes, el producto se fragmenta.

## Ownership por dominio

Cada dominio debe conservar su propia verdad operativa:

- `order` es dueño del estado del pedido
- `payment` es dueño del estado del pago
- `merchant` es dueño de configuración, políticas y capacidades del comercio

El panel del comercio debe surfacer y coordinar esa verdad. No debe colapsarla dentro de un subsistema único.

## Payments architecture

El módulo de pagos debe organizarse alrededor de un orquestador con adaptadores por proveedor.

La dirección del producto no es mantener Stripe como experiencia principal. El objetivo es migrar a **Pagopar uPay** y conservar el checkout dentro de Cerramos, de modo que el comprador no abandone nuestra URL durante el flujo normal.

### Responsabilidades mínimas

- crear la referencia o intención de pago
- inicializar el componente embebido o la sesión de cobro de uPay dentro de la UI propia
- normalizar estados del proveedor
- verificar webhooks
- asegurar idempotencia
- disparar reversiones o cancelaciones automáticas cuando aplica

### Abstracciones mínimas

- proveedor
- método de pago
- referencia externa
- estado del pago
- metadatos no sensibles

### Restricción de experiencia

- la integración principal debe ser embebida
- el frontend de checkout sigue viviendo en Cerramos
- un redirect externo solo se admite como fallback explícito del proveedor, no como contrato base

## Estados separados

La plataforma debe modelar dos máquinas distintas:

- estado del pedido
- estado del pago

Un pedido pagado todavía puede estar pendiente de confirmación operativa. Esa separación es obligatoria para no prometer algo que el comercio aún no aceptó.

## Separación pública y operativa

El tráfico público de checkout y la operación interna del comercio deben aislarse por límites de servicio y API.

Esa separación importa desde el MVP, pero no exige extracción inmediata a deployables independientes. Puede resolverse primero con boundaries explícitos dentro del monorepo y del esquema transaccional compartido.

## Entidades mínimas

- `commerce`
- `product_link`
- `product_variant_option`
- `customer`
- `customer_identity`
- `customer_consent`
- `delivery_info`
- `order`
- `order_item`
- `payment_provider`
- `payment_intent`
- `payment_event`
- `payment_risk_state`
- `order_status_history`

## Lo que la arquitectura protege

La arquitectura del MVP debe impedir tres deformaciones comunes:

- crecer hacia “mini ecommerce” antes de validar el cierre por link
- asumir responsabilidad de pasarela propia
- convertir alertas o chats en fuente de verdad operativa
